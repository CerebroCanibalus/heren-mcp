# Auditoría Heren MCP — Diseño, Mantenibilidad, Workflow y Confort

> Fecha: 2026-08-10  
> Ámbito: `crates/heren-server/`, `addons/heren/`, `src/heren/`, `tests/`, `benchmarks/`, raíz del repo.

---

## 0. Resumen ejecutivo

**Heren MCP v4 es funcionalmente impresionante** — 15 tools, plugin real de Godot, persistencia, visión off-screen, debugger integrado, autolanzamiento. Sin embargo, **la impresión de robustez se desgasta en cuanto se mira debajo del capó**: dependencias rotas, código muerto de v3, archivos binarios en git, funciones gigantes, duplicación raíz→.temp, scripts sueltos en la raíz y una barrera de entrada alta para nuevos contribuidores.

**Veredicto:** El producto es potente, pero el *proyecto* necesita una poda organizativa y una batería de tests que lo proteja de regresiones. La deuda técnica es acumulativa y ya se traduce en bugs documentados (M1–M3) y en que la codebase no compila desde cero.

## 1. Bloqueantes críticos (arreglar primero)

| # | Problema | Impacto | Ubicación |
|---|----------|---------|-----------|
| C1 | **Dependencia FlojoMCP por path inexistente** | `cargo check` / `cargo test` fallan en cualquier clon nuevo. No hay CI que lo detecte. | `crates/heren-server/Cargo.toml:16` |
| C2 | **Código v3 "eliminado" sigue en el repo** | Confusión de qué es source of truth; doble mantenimiento; tests Python apuntan al daemon muerto. | `src/heren/daemon/`, `src/heren/tools/`, `src/heren/core/session_manager.py` |
| C3 | **Archivos `.pyc`, `.uid`, lockfiles y binarios en git** | Difíciles de revisar, conflictos, repo hinchado. | `.pyc`, `.temp/target-*`, `Cargo.lock` podría discutirse |
| C4 | **Tests existentes apuntan a LAIKA** | `tests/test_tools/test_all_tools.py:12` hardcodea `D:\Mis Juegos\LAIKA\...`; no son portables ni CI-friendly. | `tests/test_tools/test_all_tools.py` |
| C5 | **Scripts y archivos temporales en raíz** | 30+ archivos en raíz (bat/py/log/json) hacen que el proyecto parezca un cajón de sastre. | Raíz del repo |

### C1 — FlojoMCP path roto

`Cargo.toml` dice:

```toml
flojo-mcp = { path = "../../../../ClaudeMCPs/FlojoMCP/crates/flojo-mcp", ... }
```

Esa ruta no existe en el workspace actual. AGENTS.md (línea 7) establece explícitamente que debe consumirse **por version, no por path**. Hasta que esto no se arregle, **nadie puede compilar el server desde un clone limpio**, lo que invalida cualquier promesa de calidad Rust.

**Recomendación:** publicar `flojo-mcp` a crates.io o, mientras tanto, usar un workspace compartido con `git`/`path` relativo dentro del repo. No una ruta absoluta fuera del repo.

### C2 — Código zombi de v3

AGENTS.md §2 dice: "Eliminados v3: godot_daemon.py, session_manager.py, heren_daemon.gd...". Sin embargo:

- `src/heren/daemon/` existe con 6 archivos `.gd` y 1 `.py` (~4.300 líneas).
- `src/heren/core/session_manager.py` (456 líneas).
- `src/heren/tools/` con 14 archivos `.py` (~4.500 líneas).

Esto es **código muerto que compite con el activo**. Los tests Python (`tests/test_daemon.py`, `tests/test_tools/test_all_tools.py`) importan estos módulos, por lo que **la suite de tests Python testea un puente que no se usa**.

**Recomendación:** mover `src/heren/daemon/` y `src/heren/tools/` a una rama `archive/v3` y borrarlos de `main`. Si se necesita fallback, resucitarlo desde git history.

### C3 — Archivos que no deberían estar en git

```text
*.pyc
*.pyo
__pycache__/
.temp/
*.uid      (salvo que se decida explícitamente versionar UIDs)
```

`.gitignore` parece incompleto o no se respeta (`src/heren/__pycache__/server.cpython-312.pyc` tiene 613 líneas contadas). Los `.uid` de Godot 4 son un debate válido, pero al menos deberían estar bajo política explícita.

### C4 — Tests acoplados a LAIKA

```python
LAIKA_PROJECT = r"D:\Mis Juegos\LAIKA\LAIKA-Solarpunk-GJ\laika-gd"
```

Esto viola el principio de AGENTS.md §3: "LAIKA SOLO pruebas" (la frase es ambigua, pero el acoplamiento no). Los tests deben crear proyectos Godot temporales bajo `tests/fixtures/` o `.temp/`.

### C5 — Raíz caótica

Conteo de archivos en raíz: ~35 archivos sueltos (`.bat`, `.py`, `.md`, `.json`, `.txt`, `Dockerfile`). Ninguna estructura de carpetas. Esto asusta a cualquier contribuidor nuevo.

## 2. Crítica de diseño

### 2.1 Arquitectura general: buena idea, fronteras borrosas

La arquitectura del server Rust → WS → EditorPlugin es **correcta** y sigue el patrón gopeak. Los puntos débiles:

1. **El server Rust es un delgado reenvío + un poco de lógica + schemas enormes.** `server.rs` tiene 1.640 líneas. La mitad son definiciones de tool (`#[tool(...)]`). Esto dificulta ver la lógica real.
2. **La lógica de negocio vive en GDScript.** Esto es inevitable porque Godot es quien muta, pero implica que el 80 % del testing real requiere un editor vivo. No hay mocks del árbol de escena.
3. **Persistencia de scene context en static `Mutex<HashMap>`** (`scene_ctx_store()`). Funciona, pero es un estado global oculto que dificulta tests paralelos y hace que el server no sea reproducible entre instancias.

**Recomendación:** separar `server.rs` en módulos por dominio (`session.rs`, `scene.rs`, `node.rs`, ...) o, al menos, extraer todos los helpers puros (`normalize_scene_path`, `args`, `unwrap_result`) a un módulo `pure.rs` testeable.

### 2.2 Split de tools v4.6: necesario, pero con coste

La decisión de partir `node`/`visual` en sub-tools (`node_query`, `node_props`, `visual_text`, `visual_image`) mejora la experiencia del agente, pero el plugin interno sigue teniendo un solo handler (`handle_get_info`, `handle_capture`). El server hace mapping. Eso está bien, pero **el schema de cada tool sigue siendo plano con ~15 argumentos opcionales**, lo que significa que la validación real ocurre en GDScript, no en el schema. Esto es flexible pero peligroso: cualquier cambio en defaults requiere tocar GDScript y Rust.

**Recomendación:** considerar schemas por `action` (subcomando) usando `oneOf` o `anyOf` en JSON Schema. FlojoMCP/schemars debería soportarlo; si no, documentar explícitamente la limitación.

### 2.3 Acoplamiento Godot ↔ Server

El plugin se conecta por WS al server. Si el server reinicia, el plugin no reconecta automáticamente (el server es quien gestiona reinicios). Esto es un punto ciego de operación.

### 2.4 Dirty tracking en el server, no en el plugin

La decisión de rastrear escenas sucias en `EditorRegistry` (Rust) en lugar de en el plugin Godot es pragmática, pero introduce una fuente de verdad duplicada: Godot ya sabe si una escena es dirty (`.is_modified()` / pestaña con punto). Si el server pierde estado (crash, reinicio), el dirty tracking se pierde.

**Recomendación:** considerar sincronizar dirty state desde Godot periódicamente, o al menos persistirlo en disco (`.heren/dirty.json`) para sobrevivir reinicios del server.

## 3. Crítica de mantenibilidad

### 3.1 Funciones gigantes

| Función | Líneas aprox. | Complejidad cognitiva | Problema |
|---------|---------------|----------------------|----------|
| `animation_handlers.gd` | 2.530 | — | Archivo monolito: animaciones + skeleton + state machines. |
| `crates/heren-server/src/server.rs` | 1.640 | — | 39 funciones de tool + helpers. |
| `handle_skeleton_get_pose` | >100 | 63 | Demasiados casos 2D/3D/bone indices. |
| `handle_input_map` | >120 | 54 | Múltiples modos (`add`, `set_events`, `remove_event`, ...). |
| `handle_setting` | >110 | 43 | Lógica de `restart_required`/`applied_runtime` mezclada. |
| `handle_blend_pose` | — | 27 | 8 de profundidad de loop transitivo. |

**Recomendación:** extraer sub-funciones con nombres declarativos. Ejemplo: `handle_input_map` debería delegar en `_input_map_add_event`, `_input_map_remove_event`, `_input_map_set_events`. Lo mismo para `handle_setting`.

### 3.2 Código duplicado

1. **`.temp/e2e_minigame/addons/heren/` es una copia del plugin.** Cualquier cambio en `addons/heren/` requiere sincronizar manualmente `.temp/`. AGENTS.md §12 lo admite: "Handlers source NO se sincronizan solos con E2E → copiar manual tras cada cambio." Eso es una trampa de mantenimiento.
2. **Lógica de coordenadas en `coords.gd` y duplicada en varios handlers.** `_node_coords()` en `node_handlers.gd`, `_shader_uniforms_to_json()` en `shader_handlers.gd`, etc.
3. **Godot executable discovery** existe en `launcher.rs` y en `src/heren/v4/godot_launcher.py`.

### 3.3 Comentarios en lugar de código claro

Muchas funciones tienen comentarios extensos explicando *por qué* se hace algo. Eso es bueno. Pero algunos comentarios explican *qué* hace el código, lo que indica que los nombres no son suficientemente claros.

Ejemplo: `ensure_plugin_installed` tiene ~100 líneas de comentarios antes del cuerpo. Una función `sync_plugin_incrementally` + `copy_or_report_failure` + `remove_orphans` hablaría por sí sola.

### 3.4 Magical strings y números

- `"res://"` repetido en decenas de lugares.
- Timeouts: 35 s en `registry.rs:298`, 1.5 s en `server.rs:304`, 1 s en `_process` de `ws_client.gd`.
- Constantes Godot version hardcodeadas en `launcher.rs` (`GODOT_CANDIDATES`).

**Recomendación:** centralizar en `const` con nombres (`TOOL_TIMEOUT_MS`, `EDITOR_KILL_WAIT_MS`, `GODOT_VERSION_CANDIDATES`).

### 3.5 Manejo de errores inconsistente

- Rust: usa `thiserror` / `ToolError`, bien.
- GDScript: retorna `{"ok": false, "error": "..."}`. Funciona, pero no hay un helper `HerenError.new(code, message, details)` estandarizado.
- Algunos handlers usan `push_error()` y retornan dict; otros solo retornan dict.

**Recomendación:** crear una clase `heren_error.gd` con códigos de error y siempre devolver el mismo shape.

### 3.6 Ausencia de contratos de API interna

No hay traits ni interfaces para handlers. Cada handler es un `Node` con métodos `handle_*`. Eso es flexible pero no impone un contrato. Un handler podría faltar `set_editor_plugin()` y romper `_enter_tree` silenciosamente.

**Recomendación:** definir una interfaz `IHerenHandler` con `set_editor_plugin(EditorPlugin)`, `register_with(Dispatcher)`. Godot 4 soporta `class_name` + `extends` con métodos abstractos documentados.

## 4. Crítica de workflow

### 4.1 Build / test

- `heren-build.bat` depende de VsDevCmd y BuildTools 2022. No hay alternativa para quien no use Windows / MSVC.
- No hay `cargo test` limpio por C1.
- No hay GitHub Actions / CI visible.
- No hay `justfile`, `Makefile` ni `xtask` para tareas comunes.

### 4.2 Instalación / setup

`install_mcp.py` registra el MCP en OpenCode. Es un paso manual. Idealmente esto debería ser `heren-server setup` o un CLI con subcomandos (`clap`).

### 4.3 Debug

- `session/diagnose` es excelente.
- Pero si el server no compila, `diagnose` no ayuda a contribuidores nuevos.
- Los logs van a `HEREN_LOG_FILE` (bien), pero hay archivos de log sueltos en `.temp/` y raíz.

### 4.4 Dependencia con Godot

La autodetección de Godot es sensible a versiones y rutas Windows. En Linux/macOS no funciona. No hay modo de pasar `GODOT_EXE` documentado de primeras.

## 5. Crítica de confort / UX

### 5.1 Para el agente (OpenCode)

- **15 tools con 30+ acciones cada una** es mucho. El agente debe recordar qué argumentos aplican a qué `action`. La documentación en `description` de cada tool es larga y se mete en el contexto del LLM.
- **Schemas planos** con todo opcional hacen que el agente no sepa qué es requerido hasta que falla `-32602`.

**Recomendación:** proveer una tool `help` o `introspect(action)` que devuelva solo los parámetros relevantes para una acción concreta. O usar `oneOf` por acción.

### 5.2 Para el desarrollador

- Encontrar dónde se implementa un `handle_*` requiere conocer el mapping de `dispatcher.gd`.
- Los nombres de handler no siempre coinciden con la tool (ej. `skeleton` → `animation_handlers.gd`).
- No hay `CONTRIBUTING.md` claro sobre cómo añadir una tool (pasos: Rust schema, GDScript handler, test Rust, test GUT, docs).

### 5.3 Para el usuario final

- Instalar requiere: Python, Rust, Godot, ejecutar scripts bat, configurar OpenCode.
- No hay release con `heren-server.exe` + instrucciones de one-liner.

| Capa | Responsabilidad | Tecnología |

### 6.4 Refactor sugerido: `server.rs`

Extraer helpers puros a `pure.rs`:

- `normalize_scene_path`
- `args`
- `unwrap_result`
- (opcional) `apply_scene_context` si se desestatica.

Esto permite tests unitarios sin instanciar el server y reduce `server.rs` a ~1.200 líneas.

### 6.5 Refactor sugerido: `animation_handlers.gd`

Dividir en 3 archivos:

- `animation_handlers.gd`: playback, tracks, keys, state machines.
- `skeleton_handlers.gd`: huesos 2D/3D, IK, FABRIK, retarget.
- `animation_utils.gd`: helpers compartidos (`_resolve_skeleton`, `_bone_chain_from`, etc.).

### 6.6 Refactor sugerido: `project_handlers.gd`

Dividir en:

- `project_setting.gd`
- `project_autoload.gd`
- `project_input_map.gd`

### 6.7 Política de UIDs

Godot 4 genera `.uid` para recursos importados. Decidir:

- A) Versionar solo los `.uid` de recursos propios (`.tres`, `.tscn`) y añadirlos a `.gitignore` para archivos autogenerados del `.godot/`.
- B) No versionar `.uid` y regenerarlos en CI.

Documentar la decisión en `AGENTS.md`.

## 9. Conclusión

Heren MCP es un proyecto ambicioso que funciona, pero **su codebase está creciendo más rápido que su estructura**. Los problemas actuales no son de arquitectura global, sino de **higiene acumulada**: código muerto, archivos sueltos, dependencias rotas, tests acoplados y funciones gigantes.

La buena noticia es que cada uno de estos problemas tiene solución mecánica y bien acotada. La mala noticia es que, si no se atajan ahora, cada nuevo feature (shader, tilemap, animation) aumentará el coste de refactor exponencialmente.

**Prioridad #1:** que `cargo test` pase en un clone limpio. Todo lo demás fluye desde ahí.

> *Herensuge vigila tu código — pero también vigila tu deuda técnica.*
